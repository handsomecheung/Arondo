# Arondo

Arondo は、コーディング タスクを AI エージェントに委任し、複数のマシンにわたる実行を監視する、モバイル ファーストの開発者ワークスペースです。 **フロントエンド + サーバー + ランナー** アーキテクチャに従っており、軽量の Go ベースのランナーが開発マシンにインストールされ、中央サーバーがすべての操作を調整します。

## 基本的なワークフロー

Arondo を使用すると、モバイル対応のワークスペースから AI エージェントに作業を委任し、変更を確認して検証し、タスクをコミットする準備ができるまで同じ会話を続けることができます。

### 1. セッションを開始する

ランナー、プロジェクト、エージェントを選択し、タスクを説明して送信します。

## オートモード

エージェント ピッカーで **自動** を選択すると、Arondo が選択したランナーにインストールされているエージェント CLI の中から選択できるようになります。 **ランナー** ページには、この選択を知らせる割り当てデータが表示されます。

自動モードでは、次の優先順位が使用されます。

1. 既知のサブスクリプション クォータを持つインストール済みの Antigravity、Claude、および Codex CLI を検討してください。 API キーで請求されたアカウントは最後の手段として保留されます。
2. 別の候補者に十分な能力がある場合、時間あたりの割り当てが 15% 未満残っているエージェントの優先順位を下げます。すべての候補者が少ない場合は、すべての候補者を利用可能な状態に保ちます。
3. 残りの候補者を、毎週のリセットまでの残り時間で調整された週ごとの割り当ての残りによってランク付けします。
4. サブスクリプション クォータが不明な場合は、API キーで請求されるエージェントにフォールバックする前に、クォータが不明なエージェントを使用してください。

## アクセス制御

**設定**から 3 つの関連コントロールを使用して認証を構成します。

- **システム アクセス トークン** は、Arondo に対してユーザーとオートメーションを認証します。完全な管理アクセス用の `admin` トークンと、制限付きアクセス用の `user` トークンを作成します。トークン値は生成時に完全にのみ表示されるため、安全に保管してください。
- **ランナー トークン** は各ランナー マシンを認証します。ランナーごとに 1 つの専用トークンを生成し、`--token` または `ARONDO_RUNNER_TOKEN` で渡します。これは、接続する最初のランナー ID にバインドされ、漏洩したトークンが別のランナーになりすますのを防ぎます。
- **ランナー アクセス制御** は、選択したランナーに個々の `user` トークンへのアクセスを許可します。管理者トークンはすべてのランナーにアクセスできます。ユーザーは、トークンを明示的に含むランナーのみにアクセスできるため、ユーザーが選択されていないランナーは管理者専用のままになります。

## アーキテクチャ

```
Browser (Next.js UI)  <--ws-->  Server (Next.js)  <--ws-->  Runner A (Go, machine-1)
                                                  <--ws-->  Runner B (Go, machine-2)
```

- **ランナー** (`runner/`): WebSocket 経由でサーバーに接続する Go バイナリ。コマンドの実行、PTY セッションの管理、git/ファイルシステム操作の実行。最小限の構成 - サーバー URL とトークンのみ。
- **サーバー**: 操作をランナーにルーティングします。すべての永続的な状態 (セッション、プロジェクト、メッセージ、ログ) を管理します。フロントエンドを提供します。
- **フロントエンド**: ランナー選択、ファイル参照、チャット、ターミナル モーダル、タスク キューを備えた単一ページの React UI。

すべての実行はランナーを経由します。サーバー上にローカル フォールバックはありません。

## 機能

- **マルチマシン ランナー**: 任意の開発マシンに Go ランナーをインストールします。 UI を使用すると、各セッションを実行するランナーを選択できます。ランナー ダッシュボードからの切断されたランナーの削除をサポートします。
- **Todo メッセージ (下書き、スケジュールされた送信、自動キューのフォローアップおよびクォータの再試行)**: 「このメッセージを後で送信する」は、ステータス/トリガー (手動、codebaseReady、afterSession、quotaAvailable、または固定時間) を持つ単一の `user-todo` チャット メッセージで、3 点メニュー (キャンセル / 今すぐ送信 / トリガーの変更) でインラインで表示されます。プロジェクトにコミットされていない変更または実行中のエージェントがある間に保存された TODO ドラフト、実行中のエージェントの背後でキューに入れられたフォローアップ、および自動クォータ枯渇の再試行が対象になります。これらはすべて、タスク ダッシュボードにファースト クラスのタスクとして表示されます。セッションでは、複数の Todo メッセージを同時にキューに入れることができます。下書き/保留中の ToDo が存在する間、チャット入力は有効なままなので、さらなるフォローアップを作成し続けることができます。チャット入力の「+」ポップアップ メニューには、「ファイルのアップロード」、「後で送信」(手動)、「クリーンな状態で送信」(codebaseReady)、および「送信スケジュール」(将来の日付/時刻を選択) があり、すべて同じ todo メッセージの配管によってサポートされています。サーバーの再起動によって送信途中でスタックしたままになっているスケジュールされた (「at」) todo は、ハングするのではなく、`failed` に自動的に解決されます。
- **セッションのアーカイブ**: 設定された期間を超えてアイドル状態のセッションを自動的にアーカイブするか、手動でアーカイブ/アーカイブ解除します。固定されたセッションは自動アーカイブから除外されます。アーカイブされたセッションは読み取り専用であるため、新しいメッセージの送信は防止されますが、履歴、ログ、差分ビューは保持されます。自動アーカイブ前のデフォルトのアイドル日数は、[設定] ページで構成できます。親プロジェクトが削除されている場合、セッションのアーカイブ解除は無効になります。プロジェクトを削除する前に、使用できなくなる可能性がある関連するアーカイブされたセッションに警告ダイアログが表示されます。
- **最近のセッション、固定、フィルタリング、および 3 点メニュー**: サイドバーは最近のセッションを中心に構成されており、個別のプロジェクト タブの代わりに軽量のアーカイブ済みセッションのヒントが表示されます。重要なセッションを一番上にピン留めし (ピン留めされたタイムスタンプ順に並べます)、必要に応じてプロジェクトまたはランナーごとにフィルターし、各セッションの 3 点メニューを使用してピン留め、名前変更、アーカイブ、または削除を行います。
- **プロジェクト準備警告**: プロジェクトにコミットされていない変更または実行中のエージェントがある場合、セッションを作成する前、または空のセッションで最初のメッセージを送信する前に警告し、とにかく送信する、準備ができたら自動送信する、または TODO セッションとして保存するオプションを提供します。エージェントがすでに実行されている場合、サーバーは常にそれを拒否するため、「とにかく送信」オプションは非表示になります。すでに履歴があるセッションのフォローアップ メッセージはこのチェックをスキップし、そのセッション自体の実行状態またはすでにキューに入れられている ToDo のみをブロックします。
- **プロジェクトの 3 点メニュー**: プロジェクト ページのヘッダーには、[ファイル ブラウザ]、[ターミナルを開く]、[変更の表示] (プロジェクトの作業ツリーのセッションレスの視覚的な差分、クリーンな場合は無効になります)、および [プロジェクトの削除] を備えた 3 点メニューが表示されます。
- **マルチユーザー トークン ベースの認証**: `admin` および `user` ロールをサポートするトークン ベースの認証でアプリケーションを保護します。まだ構成されていない場合は、最初の起動時に管理者アクセス トークンが自動的に生成されます。クライアント トークンはカスタム名と個別の色をサポートしており、これらは送信者のアバターと一緒にユーザー メッセージ カードに表示されます。管理者は、設定ダッシュボードからアクセス トークンを管理し、ランナー固有のアクセス制御リスト (ランナーを特定のユーザー トークン UUID に制限する) を構成できます。
- **安全な WebSocket 通信**: ブラウザーからサーバーへの WebSocket 接続は、`Sec-WebSocket-Protocol` ヘッダー (`arondo-token`) 経由で認証トークンを渡すことによって保護され、クエリ パラメーターやサーバー ログ内の機密の資格情報の公開を防ぎます。
- **セッションベースのワークスペース**: 各タスクは構成ディレクトリ (デフォルトでは `~/.arondo/sessions/[sessionId]/`) の下の自己完結型セッション内にカプセル化され、履歴、設定、出力を追跡します。
- **詳細な実行ログ**: すべての CLI コマンド実行の出力は、`~/.arondo/sessions/[sessionId]/logs/[messageId].log` の下に個別にログに記録され、エージェントがパイプ モードで実行されている場合、stderr は隣接する `.stderr.log` ファイルにキャプチャされます。 Stderr 出力は、エージェント実行カードのメニュー (Show Stderr) からモーダルで表示できます。
- **複数の AI エージェントのサポート**: コード生成タスク用に **Antigravity CLI (agy)**、**Claude Code**、**Codex**、および **OpenCode** をサポートします。
- **インタラクティブ ターミナル (PTY)**: エージェントとスクリプトの実行は両方とも、Go の `creack/pty` を介して完全な疑似ターミナルで実行され、`xterm.js` を使用してブラウザにレンダリングされます。インタラクティブな標準入力、ANSI カラー、およびカーソル制御をサポートします。 PTY は、ランナー出口 (SIGHUP) での信頼性の高いプロセス クリーンアップを保証します。対話型シェル端末は、サーバーではなくランナー上で直接生成されます。
- **モバイル端末キーボード バー**: 端末モーダル用のモバイル固有の特殊キー バー (ESC、TAB、CTRL、ALT、矢印、および F1 ～ F12 の FN レイヤー) が含まれています。 VisualViewport を動的に追跡して仮想キーボードの上に固定し、キーボードの障害を防ぎます。
- **専用の実行カードとリッチ マークダウン ビュー**: スクリプトの実行には `ScriptExecCard` (クイック実行コマンドのインライン ログ ストリーミングをサポート) が使用されますが、エージェントの実行には `AgentExecCard` が使用され、構文の強調表示 (`rehype-highlight`) とクリック可能なファイル/URL リンクを備えたマークダウンとして出力がレンダリングされます。検証されたファイル パスをクリックすると、リモート ファイル ブラウザが自動的に開きます。ユーザーは、フォーマットされたマークダウン出力または生のテキスト出力をカードのメニューから直接コピーできます。ユーザーは、ユーザー チャット カードの [コピー] アクションを使用してチャット メッセージをコピーすることもできます。
- **ターミナル セッションの永続性と再接続**: ターミナル セッションは、ブラウザの更新または終了イベントが発生しても存続します。ターミナルを再度開くと、ランナー上のアクティブな PTY セッションに自動的に再接続され、出力バッファが再生されます。
- **クォータとセッション制限の検出**: AI エージェント API 制限 (標準出力ログと標準エラー ログの両方をスキャンすることによる、クロードのセッション制限ヒット、コーデックス制限、または個々のクォータ枯渇やサブスクリプション アップグレード警告を含む `agy` クォータ エラーなど) を自動的に検出し、人間が判読できるエラー メッセージを表示します。
- **AI エージェント クォータ モニタリング**: ランナー上の tmux を介してクロード、アンチグラビティ、コーデックスのクォータ使用状況データを自動的に収集し、API キーの請求先アカウントを認識して、既知の残りのクォータまたは明示的な不明な状態をランナー ダッシュボードに表示します。
- **AI エージェント自動選択 (自動モード)**: 既知のサブスクリプション クォータから最適なエージェントとモデルを自動的に選択し、不明なデータよりも利用可能な容量を優先し、API キーで請求される選択肢を最後のフォールバックとしてのみ使用します。
- **手動エージェント切り替え**: エージェントがアイドル状態のときに、既存のセッション内でアクティブ エージェント (Antigravity CLI、Claude Code、Codex、OpenCode、または Auto) をオンザフライで切り替えます。
- **エージェント セッションの継続性 (再開)**: 同じセッション内の会話は、エージェント固有の履歴を保持します。 Claude Code はネイティブの再開サポートを使用し、Codex CLI は Codex セッション ID を保存して再利用し、OpenCode CLI は OpenCode セッション ID を保存して再利用し、Antigravity CLI (agy) は後続の `--conversation` 実行のために検出された会話 ID を保存します。
- **安全なプロンプトの受け渡し**: プロンプトは、一時ファイルと環境変数 (`ARONDO_PROMPT_FILE` 環境変数を使用) を使用してエージェントに渡され、シェルのコマンドラインの長さ制限を回避し、コマンド引数で機密性の高いプロンプトを公開します。 [プロンプトの表示] パネルに、元の生の入力ではなく、実際に解決されたプロンプトが表示されます。
- **同時スクリプト実行**: 単一セッション内で複数のスクリプトを同時に実行できます。ユーザーは、バックグラウンド スクリプトの実行中もチャットを続けることができます。エージェントの実行中に、プロジェクト スコープのスクリプトの実行もサポートされます。
- **グローバルおよびセッション スコープのスクリプト**: プロジェクト スコープのカスタム スクリプトをグローバル (セッションから独立し、プロジェクト パネルから直接) または特定のセッション内で実行することをサポートします。
- **設定主導のカスタム スラッシュ コマンド**: 組み込みのスラッシュ コマンド (現在のセッションの名前を変更する `/new`、`/delete`、`/rename <name>` など) とカスタム ユーザー定義エージェントのスラッシュ コマンドは、設定主導でカスタマイズ可能です。ユーザー定義のエージェント スラッシュ コマンドは、設定の **エージェント コマンド** 管理 UI (デフォルトで `~/.arondo/agent-commands.json` に保存) を介して、正規表現マッチャーと置換拡張サポートを使用して構成できます。
- **スマート チャット入力、下書き、およびファイル アップロード**: コマンド メニュー内のスラッシュ コマンドを循環するためのタブ補完をサポートします。ファイル/ディレクトリ セレクター モーダルを開いて相対パスをチャット入力に挿入するための `@` シンボル トリガーの入力をサポートします。チャット入力ではファイルの直接アップロードがサポートされています (ファイルはランナーの一時ディレクトリに送信され、解決されたパスがエージェントに渡されます)。チャットの下書きはセッションごとに `localStorage` に保持され、セッションの切り替えやクライアントのリロード後も存続します。 `!` トリガーを入力すると、プロジェクト スコープのスクリプト (オートコンプリート付き) を迅速に実行できます。これには、新しいセッションの作成中、最もよく使用される 5 つのアドホック履歴コマンド、選択したファイルをシェル コマンドとして直接実行するための「選択…」エントリ、または任意のシェル コマンドへのフォールバックが含まれます。キーボードの動作が合理化され、`Enter` でメッセージを送信し、`Ctrl+Enter` / `Meta+Enter` で改行を挿入します。また、PWA/スタンドアロン アプリを使用するためのグローバル リロード ショートカット (`F5` または `Ctrl+R` / `Cmd+R`)、およびアプリケーション全体での手動の「アプリの更新」ボタンもサポートしています。
- **リモート ファイル ブラウズとファイル ブラウザ**: プロジェクト パスを選択するときに、接続されているランナーのディレクトリを UI から直接参照します。セッションの 3 点メニューからリモート ファイル ブラウザを開きます。このブラウザには、コード構文の強調表示 (任意のサイズのファイルをサポートするためにスクロール時に 64 KB のチャンクで読み込まれる)、ワードラップの切り替え、および管理者が構成可能な隠しファイル設定が含まれます。
- **グローバル エージェント ルールの同期**: 設定 UI でグローバル エージェント ルールを構成します。これは、ランナー上の `~/.gemini/GEMINI.md`、`~/.claude/CLAUDE.md`、および `~/.codex/AGENTS.md` に自動的に同期されます。グローバル ルールは `~/.arondo/global-rules.md` に保存されます。
- **統合された差分ビューア (diff2html) とコミット履歴**: ブラウザから直接ビジュアル コードの変更を表示し、エージェント実行カードのファイル リンクから直接トリガーされるセッション全体の差分と単一ファイルのインライン差分ビューア モーダルをサポートします。 diff ビュー内で、変更された個々のファイルを動的に折りたたんだり展開したりすることをサポートします。モーダルを使用した git コミット履歴と特定のコミットの差分の表示 (コミットの表示) もサポートしています。
- **スケジュールされたタスク、自動キューのフォローアップ、クォータの再試行**: プロジェクト スコープのスクリプトを将来の固定時刻に実行するようにスケジュールします。チャット入力はエージェントの実行中もアクティブなままです。フォローアップ メッセージは、`afterSession` スケジュールされたタスクとして自動的にキューに入れられます。エージェントがクォータ制限に達した場合、クォータが使用可能になった時点で、最後のユーザー プロンプトによる再試行が自動的にスケジュールされます。
- **ランナー接続の安定性 (ハートビートとデッドリンク検出)**: Go ランナー クライアントは、定期的なハートビートを介してサーバーとの永続的な接続を維持し、読み取り期限とピンポン交換を使用してデッド WebSocket 接続を検出し、指数関数的バックオフで自動再接続します。
- **タスク キューとライブ トラッキング**: PID トラッキングとライブ ログ検査を備えたヘッダー内のアクティブなタスク キュー。タスクをクリックすると、その専用のコンソール ログ モーダルが開きます。実行中の各タスクはキューから強制終了でき、停止したプロジェクト スコープのタスクは 3 点メニューから削除できます。完了したタスクは 3 日間保持され、セッションがアーカイブされるとすぐにキューから削除されます。非表示のプロジェクトに属するタスクと Todo メッセージは、アクティブなキューとタスク ダッシュボードから自動的に除外されます。
- **タスクのグループ化、フィルタリング、インライン ログ**: タスク ダッシュボードでは、タスクをタイプ (エージェント/スクリプト) でフィルタリングしたり、デフォルトで未完了のタスクのみを表示するように切り替えたり、スコープまたはステータスごとにグループ化したりできます。スクリプト実行ログもインラインで表示できるようになりました。
- **タスクの永続性**: アクティブなタスク コンテキストは、実行メタデータをセッションおよびプロジェクトの `messages.json` ファイルに直接シリアル化することによって永続化され、サーバーの再起動時に動的に復元されます。ランナー ID は再接続後も安定しています。
- **自動化されたデータ ライフサイクル**: 親参照 (プロジェクトやランナーなど) が存在しない場合、クエリのリスト作成中にセッションやプロジェクトを自動的にパージします。
- **モバイル フレンドリーな UI**: 折りたたみ可能なパネル、モーダル ログ、応答性の高いメニュー、タッチ フレンドリーなアクションを使用して設計されています。モバイル サイドバーのセッション アイテムのスワイプして削除のジェスチャをサポートします。
- **プロジェクト管理**: 解決されたリポジトリ パス内のセッションをスコープし、追跡します。カスタム プロジェクト スクリプトと AI 自動スクリプト検出 (選択したランナー上で安全に実行) をサポートします。
- **未読セッション完了インジケータ**: バックグラウンドで実行中のセッションが完了すると自動的に追跡します (`done` または `error`)。セッションの `completedAt` タイムスタンプとユーザーの `lastViewedAt` タイムスタンプを比較します。セッションに未表示の完了がある場合、UI ではサイドバーのセッションの横に色付きのドット (成功の場合は緑、エラーの場合は赤) が表示され、ヘッダー メニュー ボタンに未読数のバッジが表示されます。
- **PWA / インストール可能なアプリ**: Web アプリ マニフェスト (`app/manifest.ts`) と登録済み Service Worker (`public/sw.js`) が同梱されているため、完全にインストールするにはフェッチ ハンドラーを備えた Service Worker が必要な Android Chrome など、スタンドアロン ウィンドウでホーム画面にアプリをインストールできます。

## はじめに

### 1. 依存関係をインストールし、サーバーを起動します

```bash
npm install
npm run dev
```

### 2. ランナーを構築して開始する

```bash
cd runner
go build -o arondo-runner .
# Pass the runner token printed in the server console on startup
./arondo-runner --server ws://localhost:3251/runner --token <runner_access_token>

# Alternatively, pass it via environment variable:
# ARONDO_RUNNER_TOKEN=<runner_access_token> ./arondo-runner --server ws://localhost:3251/runner
```

または、便利なスクリプトを使用します。

```bash
./scripts/run.runner.sh
```

### 3. UIを開く

ブラウザで [http://localhost:3251](http://localhost:3251) を開きます。接続されているランナーを選択し、プロジェクト ディレクトリを選択して、セッションを開始します。

## 設定と環境変数

- `ARONDO_CONFIG_DIR` – (オプション) 構成および実行時データを保存するカスタム ディレクトリ。開発と運用の両方で、デフォルトは `~/.arondo` になります。
- `PORT` – (オプション) サーバー ポート。デフォルトは、開発環境では `3251`、本番環境では `3250` です。
- `ARONDO_SESSION_ARCHIVE_DAYS_DEFAULT` – (オプション) アクティブなセッションが自動アーカイブされるまでのデフォルトのアイドル日数。設定で上書きが設定されていない場合に使用されます。デフォルトは `7` です。
- `ARONDO_FILE_SHOW_HIDDEN_DEFAULT` – (オプション) 隠しファイル/ディレクトリ (ドットファイル) をファイル ブラウザーおよび @ パス セレクターに表示するかどうかのデフォルト。設定でオーバーライドが設定されていない場合に使用されます。デフォルトは `true` です。デフォルトでドットファイルを非表示にするには、`false` に設定します。

### 設定ファイル (`ARONDO_CONFIG_DIR` または `~/.arondo/` 内)

- `arondo.json` – マルチユーザー アクセス トークン、ランナーごとのアクセス トークン、およびグローバル アプリ設定を含む統合ランタイム構成。次の構造で保存されます。
```json
  {
「クライアント」: [
      {
"トークン": "32 文字の 16 進文字列",
"uuid": "正規の uuid 文字列",
"名前": "表示名",
"タイプ": "管理者"
      }
    ],
「ランナー」: [
      {
"id": "トークン ID",
"トークン": "32 文字の 16 進文字列",
"name": "ランナートークン名",
"作成時刻": 1720000000000,
"lastusedAt": 1720000100000、
"boundRunnerId": "サーバー生成のランナー ID"
      }
    ],
"設定": {
"sessionArchiveDays": 7、
"showHiddenFiles": true
    }
  }
  ```
起動時に `type: "admin"` を持つトークンが存在しない場合は、トークンが自動的に生成され、構成に書き込まれ、サーバー ログに出力されます。ランナー トークンは、管理者によって [設定] ([ランナー トークン] セクション) で個別に作成および管理されます。それぞれは、それに登録された最初のランナー ID (`boundRunnerId`) にロックします。
- `global-rules.md` – 接続されたランナー上の `~/.gemini/GEMINI.md`、`~/.claude/CLAUDE.md`、および `~/.codex/AGENTS.md` にルールが同期されます。
- `agent-commands.json` – ユーザー定義のエージェント スラッシュ コマンド。
- グローバル アプリケーション構成設定は、`arondo.json` の最上位の `setitngs` フィールドに保存されます。
- `agent-sessions.json` – エージェントの会話/セッション継続性マップ。`{ "agy": {}, "codex": {}, "opencode": {} }` として保存されます。

## 自動化 API

スクリプトと外部プログラムは、UI と同じ REST エンドポイントを使用して、HTTP 経由で Arondo を直接駆動できます。 3 つのエンドポイントは、完全な作成→メッセージ→ポーリングのライフサイクルをカバーします。

### 認証

すべてのリクエストには、ヘッダーまたはクエリ パラメーターとして有効なクライアント トークンが含まれている必要があります。

```
x-arondo-token: <client_access_token>
# or
?token=<client_access_token>
```

トークンは管理者によって [設定] → [クライアント トークン (`/api/auth/client-tokens`)] から発行され、`~/.arondo/arondo.json` に保存されます。 `user` ロール トークンには、`allowedUserTokenUuids` リストを介してターゲット ランナーへのアクセスも許可する必要があります。 `admin` ロール トークンは、任意のランナーにアクセスできます。

### 1. セッションを作成する

```
POST /api/sessions
Content-Type: application/json
x-arondo-token: <token>

{
  "repoPath": "/path/to/repo",   // repository path on the runner — required unless "tempDir" is set
  "tempDir": false,              // optional — create the session in a fresh temp dir generated on the runner instead of "repoPath" (mutually exclusive with "repoPath")
  "runnerId": "runner-id",       // target runner (see GET /api/runners) — required, unless "tempDir" is set, in which case it's optional and a random available runner is picked
  "prompt": "Fix the login bug", // prompt sent to the agent; omit/blank to create an idle session
  "agentType": "auto",           // optional — "antigravity" | "claude" | "codex" | "opencode" | "auto" (default: "auto")
  "name": "My session",          // optional — defaults to first line of the prompt
  "force": false                 // optional — bypass the dirty-working-tree / already-running checks
}
```

- `tempDir: true` を設定すると、Arondo がランナー上に一時ディレクトリを生成し、それをリポジトリ パスとして使用します。その場合は、`repoPath` を渡さないでください。 `runnerId` もオプションになります。省略した場合、トークンがアクセスできるランナーの中からランダムにランナーが選択されます。
- 作成された `Session` オブジェクト (`id` を含む) を含む `201` を返します。
- リポジトリにコミットされていない変更がある場合、またはエージェントがすでに実行中で `force` が設定されていない場合は、`409 { needsConfirmation: true, reason: { dirty, busy } }` を返します。とにかく続行するには、`force: true` を再試行してください。

### 2. セッションにメッセージを送信する

```
POST /api/sessions/{id}/messages
Content-Type: application/json
x-arondo-token: <token>

{
  "message": "Also add a test for this", // required
  "force": false                         // optional — bypass the dirty-working-tree / already-running checks
}
```

- セッションの履歴に新しいメッセージを追加してエージェントを再度実行します (エージェントのセッションの継続性/再開は保持されます)。
- セッションがアーカイブされている場合は、`403` を返します。最初にアーカイブを解除してください。
- これがセッション上で送信された最初のメッセージである場合、セッション作成時と同じダーティ/ビジー確認ゲートが適用されます。`force: true` が設定されていない限り、`409 { needsConfirmation: true, reason: { dirty, busy, isFollowup: false } }` が返されます。後のフォローアップでは、このセッション自体の実行状態とすでにキューに入れられている todo メッセージのみが送信をブロックします。`409 { needsConfirmation: true, reason: { dirty: false, busy, queued, isFollowup: true } }` を返します。

### 3. セッションステータスのクエリ

```
GET /api/sessions/{id}
x-arondo-token: <token>
```

- `Session` オブジェクトを返します。 `status`、`idle`、`running`、`script-running`、`done`、`error`のいずれかをチェックします。
- `done`/`error` は、エージェントが終了したことを意味します。ステータスが `running`/`script-running` のままになるまで、このエンドポイントをポーリングします。

### スクリプト例

`bin/arondo` は依存関係のない Node.js CLI です。`send` コマンドは、セッションを作成するか、既存のセッションにメッセージを送信し、終了するまでポーリングして結果を出力します。必要なメッセージは最後の位置引数として渡されます。

```bash
bin/arondo send \
  --server http://localhost:3251 \
  --token <client_access_token> \
  --temp-dir \
  "Print the current date"
```

このコマンドはセッション ID を出力します。これを使用して、後の呼び出しで会話を継続します。

```bash
bin/arondo send \
  --server http://localhost:3251 \
  --token <client_access_token> \
  --resume \
  "Now also print the current directory"
```

`--temp-dir` または `--path` を使用せずにセッションを作成する場合、スクリプトは現在の作業ディレクトリをリポジトリ パスとして使用します。
`--runner-id` を省略すると、現在のホスト名で接続されたランナーが選択されます。ランナーが存在しない場合、または複数のランナーがそのホスト名を共有する場合は、`--runner-id` を使用します。
`--resume` を使用して、選択したランナーとリポジトリ パスの最近更新されたセッションにメッセージを送信します。 `--session-id`、`--temp-dir`との併用はできません。
`--force` を使用して `force: true` を送信し、サーバーのダーティ ワーキング ツリー確認をバイパスします。
サーバーが `needsConfirmation: true` を返すと、CLI は `--force` を再試行するためのヒントを出力します。
最終的な JSON 結果は `sessionId` を使用し、エージェントの標準出力を `rawOutput` として含めます。
最終的な JSON 結果は stdout に書き込まれます。進行状況メッセージとエラーは stderr に書き込まれます。

## ランナー CLI

```
arondo-runner [flags]

Flags:
  --server string   Server WebSocket URL (default "ws://localhost:3251/runner")
  --token string    Runner access token (optional, can also set ARONDO_RUNNER_TOKEN)
```

サーバー接続が切断された場合、ランナーは指数バックオフで自動再接続します。独自の表示名はありません。UI に表示される名前は、ランナー トークンの `name` から取得されます。これは、[設定] でトークンを生成するときに管理者によって設定されます。

## テスト

統合テストは Playwright を使用して実装されます。これらは、API エンドポイントと WebSocket 操作をエンドツーエンドでテストするために、モック構成されたサーバーと Go ランナーを生成します。

統合テストを実行するには:

```bash
npm run test:integration
```

テストランナーは次のことを行います。
1. Go ランナー バイナリをビルドします。
2. 一時構成ディレクトリ (`.arondo-test/`) を使用して、ポート `3252` で Next.js サーバーをスピンアップします。
3. Go ランナーを生成してテスト サーバーに接続します。
4. サーバー API テスト (`tests/server/`) とランナー機能テスト (`tests/runner/`) を実行します。
5. すべてのテスト プロセスを終了し、一時的なテスト構成とログを自動的にクリーンアップします。
